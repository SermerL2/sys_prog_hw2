
# Отчёт: Деление на 0 даст 0

Демонстрация перехвата `SIGFPE` через `sigaction(SA_SIGINFO)` и влияния
UB-оптимизаций компилятора на обработку деления на ноль.

**Цель работы:** изучить механизмы обработки аппаратных исключений ОС Linux
посредством разработки обработчика сигнала `SIGFPE` и исследовать влияние
оптимизаций компилятора на поведение программы при делении на ноль.

**Платформа:** Linux x86-64, gcc, clang, GNU binutils (objdump, nm, c++filt).

---

## 1. Теоретическая часть

### 1.1. Аппаратное исключение #DE

Инструкции `div` и `idiv` в архитектуре x86-64 при попытке деления на ноль
(или при переполнении частного) генерируют аппаратное исключение #DE
(Divide Error). Ядро Linux транслирует его в сигнал `SIGFPE` с кодом
`FPE_INTDIV`. Если обработчик не установлен - процесс
получает `SIGFPE` с действием по умолчанию (terminate + core dump).

### 1.2. Механизм перехвата через `sigaction` + `SA_SIGINFO`

Флаг `SA_SIGINFO` заставляет ядро передавать обработчику три аргумента:

```c
void handler(int sig, siginfo_t *info, void *ucontext);
```

Третий аргумент - указатель на `ucontext_t`, содержащий
контекст процессора на момент сбоя:

- `uc_mcontext.gregs[REG_RIP]` - адрес сбойной инструкции;
- `uc_mcontext.gregs[REG_RAX]` - старшая половина делимого (и частное);
- `uc_mcontext.gregs[REG_RDX]` - младшая половина делимого (и остаток).

Меняя эти поля, можно:

1. записать свои значения в RAX/RDX.
2. переместить RIP за инструкцию деления.

### 1.3. Кодирование инструкций div/idiv

| Опкод | Инструкция | Размер операнда | Примечание |
|-------|-----------|-----------------|------------|
| `F6 /6` | `div r/m8` | 8 бит | ModR/M.reg = 6 |
| `F7 /6` | `div r/m16/32/64` | 16/32/64 бит | ModR/M.reg = 6 |
| `F6 /7` | `idiv r/m8` | 8 бит | ModR/M.reg = 7 |
| `F7 /7` | `idiv r/m16/32/64` | 16/32/64 бит | ModR/M.reg = 7 |

Префикс REX (`0x40..0x4F`) опционален и используется для 64-битных операндов.
Длина инструкции = (префиксы) + 1 (опкод) + 1..N (ModR/M + SIB + смещение).

## 5. Объяснение результатов

### 5.1. Почему clang -O3 удаляет ветку `if (b == 0)`

Согласно стандартам C и C++, деление на ноль - undefined behavior (UB).
Это даёт компилятору право рассуждать так:

1. Программа, в которой `b == 0` на момент `a / b`, содержит UB.
2. Корректная программа UB не содержит => `b != 0` в точке деления.
3. Условие `if (b == 0)` при этом всегда ложно.
4. Ветка `then` недостижима => её код можно удалить.
5. Остаётся только `else` и printf.

Это UB-оптимизация: компилятор формирует из предположения
о невыполнимости UB выводы и упрощает программу на их основе.

### 5.2. Почему clang -O3 не удаляет сам `idiv`

- `if (b == 0)` - проверка, её результат нигде не сохраняется; при
  предположении `b != 0` она всегда ложна, и её можно выбросить.
- `a / b` - вычисление, чей результат возвращается из функции.
  Значение `b` известно только в runtime (volatile-чтение), поэтому
  результат `10 / b` нельзя вычислить на этапе компиляции.

### 5.3. Когда clang действительно убирает `div`

| Случай | Что делает clang |
|--------|------------------|
| Результат деления не используется | DCE - удаляет `div` целиком |
| `return a / b ? 1 : 0;` (unsigned) | Заменяет на `cmp a, b` + `setbe` |
| `if (a / b > 0) ...` (unsigned) | Может заменить на `cmp` |
| `return a / b;` (signed, результат нужен) | **Оставляет `idiv`** |

В нашем сценарии - последний случай, поэтому `idiv` остается.

## 6. Вывод

1. **Перехват `SIGFPE` работает** во всех четырёх сборках: обработчик
   корректно распознаёт инструкцию `idiv`, записывает 0 в RAX и RDX,
   продвигает RIP на длину инструкции.

2. **Обработчик не компенсирует UB-оптимизации.** В сборке clang -O3
   сценарий B демонстрирует принципиальный разрыв:
   - `idiv` физически присутствует и в runtime вызывает #DE;
   - обработчик срабатывает и подменяет результат деления на 0;
   - но ветка `if (b == 0)` уже удалена из машинного кода;
   - программа дает `b is NOT 0` - неверный ответ с точки зрения
     исходного кода.

3. **Уровни абстракции не совпадают.** Оптимизатор работает над исходным
   кодом и рассуждает в терминах UB. Обработчик сигнала работает на уровне
   инструкций и регистров. Между этими уровнями нет взаимно
   однозначного соответствия: удалив ветку, компилятор оставил инструкцию,
   которая может привести к логическому переходу по удаленной ветке.

4. **Практический вывод.** Перехват `SIGFPE` - инструмент диагностики
   и отладки, а не замена корректной обработке ошибок. Единственный
   надёжный способ обработки деления на ноль - явная проверка делителя
   до деления:

   ```c
   if (b == 0) {
       /* обработка */
   } else {
       result = a / b;
   }
   ```

   При этом `b` должна быть `volatile`, иначе оптимизатор вправе удалить
   и эту проверку - как следующую из предположения «UB не наступает».
